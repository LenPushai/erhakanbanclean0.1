## Security Goal — ACHIEVED

RLS is enabled on `public.signature_tokens`. The threat model behind US-023.5 (anonymous enumeration of pending signature tokens) is closed.

Verified:
- `ALTER TABLE public.signature_tokens ENABLE ROW LEVEL SECURITY;` applied (commit `67d22fc`).
- Direct anon-key attack probe against the table returns `[]` — anon can no longer enumerate tokens.
- Service-role JWT decoded at runtime: `role: "service_role"` confirmed via `/api/envcheck`.

**Do not disable RLS.** The security win stands. The feature breakage below is acceptable overnight because the e-sign flow is not yet in live use by the team — only Len's own test path is affected.

## Open Puzzle — service-role read returns empty

`/api/sign-tokens-list` returns `{tokens: []}` despite at least one manager-stage token known to exist in the DB. Service role should bypass RLS but the `@supabase/supabase-js` client is seeing no rows.

What we have already confirmed:
- All three env vars are present in the runtime: `SUPABASE_URL`, `SUPABASE_ANON_KEY`, `SUPABASE_SERVICE_ROLE_KEY`.
- The service-role key's JWT `role` claim decodes to `service_role` (not `anon`, not a typo).
- Anon probe against the same URL returns `[]` as expected (RLS doing its job).
- Service-role probe against the same URL **also** returns `[]` — that is the anomaly.

## Hypotheses to test tomorrow (in rough order of likelihood)

1. **Mismatched URL ↔ key project pair.** The `SUPABASE_URL` and the service-role key may belong to different Supabase projects. JWT decode confirms the role but not the project ref. Check the `ref` claim in the JWT against the URL subdomain.
2. **JWT signing-secret rotation.** If the project's JWT secret was rotated after this service-role key was generated, the key would still decode locally but PostgREST would silently treat it as unauthenticated → falls back to anon → blocked by RLS → empty result with no error.
3. **`supabase-js` library quirk with legacy keys.** Recent `supabase-js` versions changed how legacy/long-lived service-role keys are handled. Worth pinning behavior with a raw `fetch` to PostgREST (the `42991cc` probe already adds this scaffolding) and comparing to the client call.
4. **PostgREST `Prefer` / `Accept-Profile` header issue.** If the client is sending a schema/profile header that doesn't match `public`, PostgREST may serve from a different schema where the table is empty.
5. **REST vs RPC behavior divergence.** Worth a sanity check that a raw REST `GET /rest/v1/signature_tokens` and an RPC call return the same shape, in case there's an unexpected view/policy interaction.
